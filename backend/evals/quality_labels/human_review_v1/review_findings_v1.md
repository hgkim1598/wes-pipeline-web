# 설명 품질 검사기 — 검토 결과 정리 v1

- 사용자 판단: HR01~HR04, 4개 → `responses.json` (`labelSource: human`)
- AI 검토: HR05~HR20, 16개 → `ai_review_v1.json` (`labelSource: ai_review`, 사람 정답 아님)
- **전체 20개는 독립 성능 평가 데이터가 아니다.** 모두 규칙을 만들고 고칠 때 본 개발 데이터이고(HR03·HR12는 합성 문장),
  판정이 다양하게 나오도록 고른 사례라 무작위 표본도 아니다. 사람 검증이 끝난 것은 4개뿐이다.
- Precision·Recall·F1은 계산하지 않았다. 아래 건수는 참고용이며 검사기 정확도가 아니다.

## 1. 사용자 판단과 검사기 (HR01~HR04)

| 사례 | 사용자 Q1 / Q2 | 검사기 | 비교 |
|---|---|---|---|
| HR01 read | 오류 / 정상 | FAIL `never_explained` (답변 전체에서 설명 0/4) | Q1 일치. Q2 불일치: 사용자는 summary 문장으로 이해했다고 판단했고, 검사기는 read의 뜻풀이가 없으면 설명이 없다고 본다 |
| HR02 dbSNP/rsID | 정상 / 정상 | PASS `explained` | 일치 |
| HR03 깊이 [synthetic] | 정상 / 해당 없음 | FAIL `inaccurate_gloss` | 불일치. 사용자는 이해도를 판단했고, 검사기는 정확성을 판단했다(아래 3절) |

사용자 메모는 네 사례 모두 "이해도 판단이며 과학적 정확성 검증이 아님"이라고 밝힌다. 사용자 판단은 이 범위로만 읽는다.

## 3. HR03 정의의 과학적 정확성 (AI 의견)

"평균 깊이(target 염기 중 read에 덮인 비율)"는 **틀린 정의**다.

- 깊이는 한 위치를 read가 **몇 번** 겹쳐 덮었는지(횟수, 단위 ×)다.
- "덮인 비율"은 1× 이상으로 덮인 염기의 비율(breadth)이라는 다른 지표다. 실행 기록에도 1X = 90.7095%로 따로 있다.
- 한 문장 안에서 '비율'과 '11.0116배'가 서로 맞지 않는다.

사용자 '정상'은 이해도 판단이므로 그대로 둔다. 그럴듯하게 읽히는 틀린 설명은 초보자 이해도 검토로는 걸러지지 않는다는 점을 보여 주는 사례다.

## 4. 발견된 문제 (확인된 것만)

| 유형 | 대표 사례 | 근거 | 고칠 곳 |
|---|---|---|---|
| A. 용어 뜻 누락 | HR01 read, HR08 깊이, HR11 dbSNP, HR05 BAM | 사용자 HR01 Q1 오류 + AI | 프롬프트·Knowledge (검사기는 이미 잡음) |
| B. 과학적으로 틀린 설명 | 합성 HR03, HR12만 | 실제 답변 18개에서는 확인되지 않음. 경미한 부정확성은 HR06(MD), HR08('합친 값') | 검사기(단서 단어만 봄), 사람·전문가 검토 |
| C. 정의는 맞지만 문장이 어려움 | HR01·HR04·HR16 "겹치지 않는 염기/겹치지 않게 센 목표 염기", "염기 단위", "read에 한 번도 덮이지 않았다" | **사용자 메모(HR01, HR04)** | Knowledge·payload 표현 (필드 이름을 직역할 문구만 있음) |

| E. 내부 표현 노출 | HR15, HR18, HR05(completed_with_warnings, raw VCF), HR16 | AI + 검사기 | 프롬프트, 검사기(HR16 유형 추가) |
| F. 중요한 실행 사실 누락 | HR19(경고 수·단계 없음), HR20(경고 수는 단서 문장에만, 단계 이름 없음) | AI | 프롬프트, 검사기 규칙 |
| G. 검사기 오판 | HR16 미탐, HR20 너그러운 PASS, HR05 설계 의도와 다른 FAIL | AI | 검사기 |

웹에서 열 수 없다(`docs/WES_DESIGN_PLAN.md` 18-3 #6). 사용자가 할 수 없는 확인을 권하는 문제라서 **Backend·화면 설계**에서 다룰 일이다.

## 5. 당장 개선할 가치가 높은 항목

1. **검토 질문을 '이해도'와 '정확성'으로 나누기** (검토 설계)
   - 왜: HR03에서 사용자는 이해도를 판단했는데, Q1은 정확성까지 묻고 있었다. 네 메모 모두 정확성은 판단할 수 없다고 했다.
   - 기존과 차이: Q1 하나에 두 가지를 섞어 묻던 것을, 초보자 이해도와 출처 대조 정확성(전문가 또는 출처 확인)으로 나눈다.
   - 검증: 같은 사례를 새 질문으로 다시 검토해, HR03 같은 불일치가 두 축으로 나뉘어 설명되는지 본다.
2. **경고 사실 규칙 강화** (검사기)
   - 왜: HR20은 단계 이름 없이 단서 문장 속 '세 단계'만으로 PASS가 됐다. HR19는 REVIEW로만 남았다.
   - 기존과 차이: '경고 수 또는 단계'를 답변 어디서든 찾던 것을, '수와 단계 이름'을 summary나 importantFindings에서 찾도록 바꾼다.
     단서 문장(uncertainties)에서만 찾으면 REVIEW로 한다.
   - 검증: HR19·HR20 답변과 기존 baseline을 모델 호출 없이 다시 채점하고, 바뀐 판정을 하나씩 사람이 확인한다.
3. **필드 이름 직역 표현 탐지** (검사기 + Knowledge)
   - 왜: HR16 미탐. 사용자도 HR01·HR04 메모에서 같은 표현을 어렵다고 했다.
   - 기존과 차이: payload 필드와 파이프라인 메시지에서 나온 직역 표현 목록(예: "겹치지 않는 염기")을 REVIEW로 잡는다.
     근본 해결은 Knowledge에 쉬운 문구("겹치는 구간을 한 번만 센 target 염기" 등)를 주는 것이다.
   - 검증: HR16 문장(양성)과 같은 뜻을 쉬운 말로 쓴 문장(음성)으로 단위 테스트를 만든다. 새 답변에서 사람 판정과 대조한다.
4. **수치 옆에 뜻과 해석 기준 쓰기** (프롬프트·Knowledge)
   - 왜: 사용자가 HR03에서 "11배가 높은지 낮은지, 어떤 의미인지" 모른다고 직접 밝혔다. HR08도 같다.
   - 기존과 차이: 깊이·0× 비율 같은 수치를 쓸 때 같은 항목에 '무엇을 센 값인지'와 '이 프로젝트에 기준이 있는지'를 함께 쓰게 한다.
     없는 기준을 지어내지는 않는다.
   - 검증: 새 답변에서 해당 항목만 보고 사용자가 수치의 뜻을 말할 수 있는지 확인한다(모델 호출 승인 필요).
5. **정책 결정 두 가지** (기준 문서)
   - 왜: HR01 Q2(사용자 정상 ↔ 검사기 never_explained)와 HR05(단계 이름 속 BAM)에서 판정이 정책에 따라 갈린다.
   - 기존과 차이: read처럼 문맥으로 이해되는 용어에도 뜻풀이를 요구할지, 바꿔 쓴 단계 이름 속 용어를 셀지 정해 v2 기준에 적는다.
   - 검증: 정한 정책으로 기존 20개의 판정이 어떻게 바뀌는지 표로 확인한다. 규칙은 그 뒤에 고친다.

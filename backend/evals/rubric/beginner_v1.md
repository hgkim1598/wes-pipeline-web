# 초보자 평가 기준 v1 (`beginner_v1`)

WES Diagnostic Agent가 만든 실행 설명을 **WES 분석을 처음 접하는 연구자** 관점에서
사람이 채점하기 위한 기준이다.

- 이 기준은 사람 검토자가 답변과 근거를 읽고 판단하는 데 쓴다. 실제 사용자를 대상으로
  한 이해도 시험이 아니며, 점수는 "초보자가 이해할 수 있을 것으로 검토자가 판단했다"는
  뜻이다.
- 자동 검사(`evaluators.py`의 deterministic 결과)와 사람 평가는 서로 대체하지 않는다.
  자동 검사가 모두 PASS여도 이 기준의 점수는 낮을 수 있다.
- 점수가 확실하지 않으면 임의로 정하지 않고 `pending_review`로 남긴다.

## 채점 규칙

| 값 | 뜻 |
|---|---|
| `2` | 기준을 충족함 |
| `1` | 일부만 충족함 |
| `0` | 충족하지 못함 |
| `N/A` | 그 사례에는 해당 항목을 평가할 대상이 없음 (B5에서만 허용) |
| `pending_review` | 검토자가 근거를 들어 점수를 확정할 수 없음 |

- 판단은 **답변 전체**(summary, importantFindings, limitations, nextChecks,
  uncertainties)를 대상으로 한다.
- 각 점수에는 답변의 해당 문장을 인용해 근거를 남긴다.
- 한 문제는 가장 직접 관련된 항목 하나에서만 감점한다. 예를 들어 해결책을 지어낸 것은
  B5가 아니라 B3에서 감점한다.

## B1 진행 상황 설명

**질문:** 실행이 어디까지 진행됐고 어디서 멈췄는지(또는 모두 끝났는지)를 초보자가 알 수 있는가?

| 점수 | 기준 |
|---|---|
| 2 | 완료된 단계, 멈춘(또는 마지막) 단계, 시작되지 않은 단계가 모두 드러난다 |
| 1 | 최종 상태는 알 수 있으나 어느 단계까지 진행됐는지가 빠지거나 모호하다 |
| 0 | 진행 상황을 알 수 없거나, 실행되지 않은 단계를 실행된 것처럼 말한다 |

- 2점 예: "입력 확인부터 정렬까지 네 단계는 끝났고, BAM 정리·보정 단계에서 실패했습니다. 이후 단계는 시작되지 않았습니다."
- 1점 예: "실행이 실패했습니다. 검증 과정에서 문제가 있었습니다."
- 0점 예: "변이 호출 결과를 확인할 수 없었습니다." (변이 호출 단계가 시작되지 않았다는 사실 없이 결과만 없다고 말함)

**선택 이유:** WES 실행은 길고 여러 단계로 이루어진다. 초보자가 가장 먼저 알아야 하는 것은
"어디까지 됐는가"이며, Frontend 원칙(현재 단계·완료 단계·남은 단계 표시)과 같은 질문이다.

## B2 필수 전문용어 설명

**질문:** 이 사례의 핵심 사실을 표현하는 데 빠질 수 없는 전문용어를 초보자가 이해할 수 있게 설명했는가?

**필수 용어의 정의:** 그 용어 없이는 사례의 "반드시 말해야 할 사실"을 표현할 수 없는 도메인
개념이다. 검토자가 답변을 읽은 뒤 고르지 않고, **사례 spec에 미리 적어 둔다.** 사례 spec에
필수 용어가 없으면 B2는 `pending_review`로 남긴다.

| 점수 | 기준 |
|---|---|
| 2 | 필수 용어가 모두 설명됐거나, 용어 없이 쉬운 말로 바꿔 같은 사실을 전달했다 |
| 1 | 필수 용어 중 일부만 설명됐다 |
| 0 | 필수 용어가 설명 없이 쓰였다 |

- **쉬운 말로 바꿔 쓴 경우도 충족으로 인정한다.** 예: "BAM"을 쓰지 않고 "정렬된 읽기 결과 파일"이라고만 써도 충족.
- 2점 예: "BAM 파일(정렬된 읽기 결과를 담은 파일)을 검사했는데 통과하지 못했습니다."
- 0점 예: "markdup BAM의 quickcheck가 실패했습니다."
- 필수 용어가 아닌 용어(도구 이름 등)를 설명하지 않은 것은 감점하지 않는다. 대신 근거에 메모만 남긴다.

**선택 이유:** 용어를 모두 풀어 쓰면 설명이 길어지고, 하나도 풀지 않으면 초보자가 읽을 수 없다.
"사실 전달에 꼭 필요한 용어"로 범위를 미리 정해야 검토자마다 기준이 달라지지 않는다.

## B3 확인된 사실과 근거 없는 추론 구분

**질문:** 근거가 있는 사실과 근거 없는 추측을 구분했는가? 원인을 지어내지 않았는가?

다음 두 가지를 구별한다.

- **근거 없는 추론:** 근거 데이터에 없는 해석·연결을 덧붙임. 단정하지 않고 추측임을 드러내면 가벼운 문제다.
- **근본 원인 단정:** 근거에 원인이 없는데 "~ 때문에 실패했다"처럼 원인을 사실로 말함. 또는 근거 없는 해결책을 지어냄. 무거운 문제다.

| 점수 | 기준 |
|---|---|
| 2 | 모든 문장이 근거에 있는 사실이거나, 근거에 있는 한계·불확실성을 그대로 전달한다 |
| 1 | 근거 없는 추론이 있으나 단정하지 않았다. 또는 기록된 실패 자체를 "원인"이라고 부르는 등 표현이 사실 범위를 약간 넘는다 |
| 0 | 근본 원인을 단정하거나, 근거 없는 해결책·조치를 제시한다 |

- 2점 예: "검증이 왜 실패했는지는 제공된 데이터로는 알 수 없습니다."
- 1점 예: "이 값은 검증이 실패한 BAM에서 나온 값이므로 의미를 판단할 수 없습니다." (근거에 없는 연결이지만 결론을 단정하지 않음)
- 0점 예: "참조 유전체가 맞지 않아 검증이 실패했습니다. 참조 파일을 바꿔 다시 실행하세요."

**선택 이유:** 이 Agent에서 가장 피해야 할 실패는 그럴듯한 원인을 지어내는 것이다. 다만 가벼운
추론까지 0점으로 처리하면 심각한 단정과 구별할 수 없어서 두 단계로 나눈다.

## B4 알 수 있는 것과 없는 것 설명

**질문:** 이 데이터로 알 수 없는 것을 초보자가 알 수 있게 밝혔는가?

| 점수 | 기준 |
|---|---|
| 2 | 사례 spec의 "반드시 인정해야 할 한계"를 모두 밝혔다 |
| 1 | 일부만 밝혔다 |
| 0 | 한계를 밝히지 않았거나, 알 수 없는 것을 아는 것처럼 말했다 |

- 사례 spec에 한계 목록이 없으면, 검토자가 근거 데이터에서 확인한 한계를 근거와 함께 적고 점수를 매긴다. 확인이 어렵다면 `pending_review`로 남긴다.
- 2점 예(필수 한계가 "실패 원인 미상, 이후 단계 결과 없음"인 경우): "이후 단계가 실행되지 않아 커버리지나 변이 결과는 없습니다. 검증이 왜 실패했는지는 알 수 없습니다."
- 0점 예: 이상이 없는 실행에서 "품질이 충분합니다"라고 판정함(합격 기준이 설정되지 않았는데 판정함).

**선택 이유:** 초보자는 설명에 없는 것을 "문제없음"으로 읽기 쉽다. 결과를 얼마나 신뢰할 수
있는지 판단하려면 모르는 부분이 드러나야 한다.

## B5 다음 확인 사항의 이해 가능성

**질문:** 제시한 다음 확인 사항을 초보자가 읽고 무엇을, 어디서 확인할지 알 수 있는가?

| 점수 | 기준 |
|---|---|
| 2 | 무엇을 확인할지와 어디서(어떤 화면·파일·값) 확인할지를 초보자가 알 수 있다 |
| 1 | 무엇을 확인할지는 알 수 있으나 위치나 방법이 전문가 표현이라 따라 하기 어렵다 |
| 0 | 근거 있는 다음 확인 사항이 있는데 제시하지 않았거나, 제시했지만 이해할 수 없다 |
| N/A | 근거 데이터에 다음 확인 사항이 없는 사례(예: 실패 code에 grounding이 없음)이고, 답변도 지어내지 않았다 |

- **N/A 규칙:** 사례 spec에 "근거 있는 다음 확인 없음"이 적혀 있거나 검토자가 근거 데이터에서 이를 확인한 경우, 비어 있는 nextChecks는 N/A다.
- **해결책을 지어낸 경우:** B5가 아니라 B3에서 0점으로 평가한다. B5는 N/A로 둔다.
- 2점 예: "커버리지 결과 화면의 '20배 이상 비율'을 확인하세요."
- 1점 예: "결과 지점은 core 요약 문서의 해당 필드에서 확인할 수 있습니다." (어떤 필드인지, 초보자가 그 문서를 어떻게 여는지 알 수 없음)

**선택 이유:** 근거가 없는 사례에서 확인 사항이 비어 있는 것은 올바른 행동이다. 이를 감점하면
조치를 지어내도록 유도하게 되므로 N/A를 둔다.

## B6 핵심 결론의 우선 제시

**질문:** 가장 중요한 결론(실행 상태와 결과)이 맨 앞에 오는가?

| 점수 | 기준 |
|---|---|
| 2 | summary 첫 문장에 실행 상태와 결과(멈춘 위치 또는 완료)가 함께 있다 |
| 1 | 결론은 summary에 있으나 첫 문장이 아니거나, 첫 문장에 상태와 결과 중 하나만 있다 |
| 0 | summary에서 결론을 찾을 수 없다 |

- 2점 예: "이 실행은 BAM 정리·보정 단계에서 실패해 중간에 멈췄습니다."
- 1점 예: "이번 실행은 실패 상태로 끝났습니다." 뒤에 단계가 이어짐 (첫 문장에 상태만 있음)

**선택 이유:** 초보자는 첫 문장만 읽고 판단하는 경우가 많다. "끝났는가/어디서 멈췄는가"가
먼저 와야 나머지 세부 내용을 읽을 이유가 생긴다.

## 별도 사람 검토 항목 (점수 없이 판정)

초보자 이해도와 별개로, 답변이 근거와 실제로 맞는지 확인한다. 판정은 `pass` / `fail` /
`pending_review`이고, 문제가 되는 문장을 인용한다.

### H1 문장과 인용 근거의 실제 일치

- 각 문장의 내용이 그 문장이 인용한 근거(evidenceRefs)에 실제로 있는가?
- 자동 검사의 `numbers-preserved`는 숫자가 **어딘가의** 사실 값과 같은지만 본다. H1은 그 숫자가 **인용한 근거의 해당 의미**와 맞는지를 본다.
- 여러 근거를 인용한 문장은 근거를 합쳐 문장 내용을 뒷받침하면 `pass`다.
- 근거 본문(payload, Tool 반환값)이 기록에 없으면 run을 재생성해 대조하거나 `pending_review`로 남긴다.

### H2 근거 없는 인과관계 주장

- "~ 때문에", "~이므로", "~로 인해"처럼 인과를 말하는 문장 중 근거에 그 인과가 없는 것이 있는가?
- 하나라도 있으면 `fail`로 판정하고 문장을 인용한다. 단정하지 않은 문장이어도 기록한다. 점수 영향은 B3에서 판단한다.

## 자동 검사 후보 (이번 범위에서는 구현하지 않음)

### A1 단위

- **목적:** 단위가 있는 측정값을 단위 없이 쓰거나 다른 단위로 쓴 문장을 찾는다.
- **한계와 오탐 위험:**
  - 현재 숫자 수집은 key를 구분하지 않는다. 같은 숫자가 단위 있는 key와 단위 없는 key에 함께 나오면 어느 의미로 쓴 것인지 알 수 없다.
  - 단위 표기가 다양하다(%, 퍼센트, 배, ×, X).
  - payload(camelCase)와 Tool 반환값(snake_case)의 key 형식이 다르다.
  - 0–20 정수는 현재 숫자 검사에서 제외된다.
  - 파이프라인 metric의 실제 단위가 이름과 다를 수 있다. 예: `percent_duplication`은 Picard `PERCENT_DUPLICATION` 원값(0–1 비율)을 그대로 기록한다.
- **설계 원칙:** 그 숫자와 일치하는 **모든** 사실 key의 단위가 같을 때만 지적한다. 그 밖의 경우는 "모호"로 따로 세고 지적하지 않는다.

### A2 인과 표현

- **목적:** "때문에", "이므로", "로 인해" 등 인과 표현이 있는 문장을 H2 검토 **후보로 표시**한다.
- **한계:** 근거에 인과가 있는 정당한 문장도 걸린다. **자동 감점하지 않는다.**

### A3 근거 범위

- **목적:** 문장이 인용한 근거 밖의 내용을 담는지 자동으로 확인한다.
- **이번 구현 범위에서 제외한다.** summary에는 근거 참조가 없고, 개수를 세어 만든 문장은 근거와 직접 대응하지 않는다. 또한 저장된 평가 기록에는 payload와 Tool 반환 본문이 없다.

### A4 정보 밀도

- **목적:** 문장 수, 숫자 개수, 전문용어 개수 등으로 답변이 지나치게 빽빽한지 본다.
- **참고 지표로만 사용한다.** 통과/실패 판정이나 점수에 반영하지 않는다.

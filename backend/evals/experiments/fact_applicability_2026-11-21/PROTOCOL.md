작성: 2026-11-21, 제품 코드를 바꾸기 전. 정답 키는 `answer_key.json`, 실행은
`run_eval.py`, 결과는 `results_before.json`(현재 코드) · `results_after.json`

## 무엇을 고치려는가

2026-11-21 구조 분석에서 확인한 두 원인.

- R1 관측 사실과 일반 지식이 같은 근거 ID(`dx:`, `fail:`, `step:`)로 묶여
  모델 입력·검증·화면에서 구분되지 않는다.
- R2 지식·파이프라인 문구에 "뒤 단계가 실행됐다"는 전제가 있는데 이 Run의
  실행 사실과 대조하지 않는다. 실제 사례: 00 단계에서 실패해 01(FastQC)이
  실행되지 않은 Run에 "개별 FastQC 리포트는 정상적으로 생성되었습니다"가
  화면과 모델 입력에 들어갔고, 제공된 답변 4건이 이를 옮겼다.

R3(숫자·주장·근거 결속)은 이번 변경 대상이 아니다. 기존 Gate 6·7이 약해지지
않는지만 본다.

정답 키는 각 사례의 **원본 기록**(단계 문서, run_status.json)에서 정했다. 구현
코드의 판정을 보고 정한 값이 아니다.

결과를 보며 규칙을 맞추지 않는다. 같은 개발자(AI)가 쓴 합성 사례이므로 완전한
독립 평가는 아니다.

## 단계 실행 상태 (장부) 정의

| 값 | 뜻 | 판정 근거 |
|---|---|---|
| ranCompleted / ranWarning / ranFailed | 실행됨, 끝 상태 | 단계 문서의 status |
| skipped | 파이프라인이 건너뜀 | 단계 문서 status=skipped |
| running | 실행 중 | 끝나지 않은 Run의 current_step |
| waiting | 아직 차례가 오지 않음 | 끝나지 않은 Run, 단계 문서 없음 |
| notRunAfterFailure | 앞 단계 실패로 실행 안 됨 | 실패로 끝난 Run, 앞에 ranFailed 단계 |
| notRunCancelled | 취소로 실행 안 됨 | 취소된 Run, 단계 문서 없음, 실행 중 표시 아님 |
| notRunAfterStop | 요청 범위 밖이라 실행 안 됨 | pipeline status = stopped_at_requested_step |
| unknown | 판정 불가 | 위에 해당하지 않음. 예: 끝난 Run인데 "실행 중"으로 남은 단계, 완료 Run의 문서 없는 단계 |

단계 목록 자체가 없으면 단계별 판정을 만들지 않고 "단계 목록 없음"으로 둔다.

## 적용 판정

- applicable / notApplicable / unknown. unknown을 applicable로 보지 않는다.
- notApplicable과 unknown은 Run 설명(모델 입력, 화면의 결과 설명)에서 뺀다. 뺀
  것과 이유는 기록한다.

### 모순 검출기 (평가 전용, 여기서 고정)

정답 키가 "실행되지 않음"(미실행 · 계획 밖)으로 정한 단계에 대해서만 켠다.
문장 단위 정규식이며 다른 표현은 놓칠 수 있다. 제품 Gate가 아니다.

## 성공 기준 (2026-11-21 새로 정함, 과거 목표 아님)

1. 단계 상태 정답: 개발·보류 모두 100%.
2. 지식 문장 분류: 100%. 분류 근거(필드 역할 기본값 / 개별 검토)를 따로 센다.
3. 모순되는 입력 문장: 구현 뒤 모든 사례에서 0.
4. 화면의 모순된 설명: 구현 뒤 실제 화면 0, 표시 데이터 0.
5. 잘못 보류: 0.
6. unknown을 applicable로 처리한 경우: 0.
7. 기존 Gate: 지원 유형 탐지가 100%로 유지되고 정상 답변 오차단이 0. payload가
   바뀌므로 분모 변화는 그대로 보고한다.
8. 추가 처리 시간: 사례별 중앙값 50 ms 미만.

- 검출기는 정해 둔 문형만 센다. 0건이 "모든 모순이 없다"는 뜻은 아니다.
- 이 실험은 모델 입력과 화면을 본다. Claude를 호출하지 않으므로 바뀐 입력으로
  모델 답변이 실제로 달라지는지는 측정하지 않는다.
- 테스트 통과는 AI 설명의 의미 정확도가 아니다.

## 안전

Claude CLI 호출 없음. 파이프라인 실행 없음. 실제 Run은 기존 eval 복원 함수로
임시 폴더에 복원해 읽는다. 원본 Run · DB · capture에는 쓰지 않는다. 결과에는
sample/run 식별자를 쓰지 않는다.

## 사후 변경 (결과를 본 뒤 바꾼 것)

1. **평가기 결함 수정 (기준 변경 아님).** `expected_steps`가 `"fromDocument"`
   단계 문서를 임시 Run 디렉터리가 지워진 뒤 읽어, 해당 단계의 기대값이 모두
   `unknown`이 됐다. 중간 결과(`results_mid.json`)의 단계 불일치 일부가 이
   결함 때문이다. 기대값을 `with` 블록 안에서 계산하도록 고쳤다. 정답표와 성공
   기준은 바꾸지 않았다. RED(`results_before.json`)는 장부가 없어 이 결함과
   관계없이 0이다.
2. **제품 결함 수정 — 보류 사례 H1에서 처음 발견.** 리더가 끝난 Run의
   `current_step`을 지워, 취소 시점에 진행 중이던 단계가 장부에 `pending`으로
   와서 `notRunCancelled`로 판정됐다(정답 `unknown`). 1차 보류 결과 H1은 7/8
   이었다. 원래 기록된 current_step을 장부까지 전달하도록 고쳤다. 보류 사례를
   보고 고친 것이므로, 수정 뒤 H1 결과는 더 이상 "보지 않은 사례"의 성적이 아니다.
3. **정답표는 그대로 둔 사례.** agent_warning_step의 MULTIQC_FAILED 영향 문구
   "레인별 FastQC 결과는 그대로 있습니다"는 테스트용 합성 문장으로, main.sh에
   없는 미등록 문구다. 설계 원칙(미등록 문구는 적용 여부 unknown → 보류)에 따라
   보류된다. 정답표는 이 문장을 남겨야 한다고(mustRemain, unknownAllowed=false)
   정해 두었으므로 지표 5에서 잘못 보류로 센다. 정답표를 고쳐 0으로 만들지 않는다.
4. **평가기 중복 집계 수정.** 지표 5에서 한 문장이 "unknown 보류 불허"와
   "mustRemain" 두 규칙에 동시에 걸리면 2건으로 셌다. 문장 단위로 한 번만 센다.
   (agent_warning_step: 2 → 1. 정답표 변경 없음.)
5. **실제 화면 검출 범위.** 지표 5 ①을 처음에는 페이지 전체 DOM에 적용했다. 그러면
   "개발자 정보 — 서버 원본 응답" 패널(`<pre>`)이 API JSON을 그대로 보여 주는 부분까지
   센다. 그 패널은 실행 기록 원문(impact)과 보류 판정 목록(보류한 문장 자체와 이유)을
   일부러 그대로 보인다. 그래서 `<pre>` 안을 빼고 세고, 원본 패널 일치 수는 따로
   적었다(전 2, 후 2 — 둘 다 기록 원문). 이 범위는 결과를 본 뒤 정했다.
   또 "전" 화면은 이미 바뀐 frontend와 지식 파일 위에서 이전 backend 응답으로 그린
   것이다. 이전 지식 문장 "개별 FastQC 리포트는 정상적으로 생성되었습니다"가 화면에
   보였던 것은 작업 전 :8000 응답과 기록 원문으로 확인했고, 이 "전" 화면에는 영향 문구
   "Per-lane FastQC still runs"만 남아 있었다.

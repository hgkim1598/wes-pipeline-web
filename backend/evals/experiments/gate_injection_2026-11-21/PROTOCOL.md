# 런타임 검증 Gate 오류 주입 실험 — 프로토콜 (실행 전 작성)

작성: 2026-11-21, 실행 전. 결과는 `RESULTS.md`와 `results.json`에 따로 남긴다.

## 무엇을 재나

`app/services/explanation/llm/synthesis.py`의 `_check()`가 실제 서비스에서 모델 답변마다 돌리는 검사다.
같은 함수를 그대로 부른다. 이 실험을 위해 검사 코드를 고치지 않는다.

| 검사 (finding 이름) | Gate | 설계상 잡는 것 |
|---|---|---|
| `invalidSynthesis` | 2 (Pydantic 재검증) | 구조 위반. 예: `evidenceRefs`가 비어 있음 |
| `sensitiveOutput` | 내용 검사 중 첫 번째 (8-gate 목록 밖, 2026-11-17 추가) | 경로·이메일 모양, 이 Run의 sample/run/job id 문자열 |
| `unknownEvidenceRef` | 3 | payload나 Tool이 발급하지 않은 근거 ID |
| `unsupportedNumber` | 4 | 사실 집합 어디에도 없는 숫자. 단 0~20 정수는 검사하지 않음 |
| `internalFieldName` | 5 | payload의 camelCase 키 이름이 문장에 나옴 |
| `runFactMismatch` | 6 | 좁은 문형만 봄: "평균 깊이 N배", 0× 염기 N%/개, 변이 후보 기록 N개/건, 경고 단계 수, 경고로 끝나지 않은 단계를 경고라고 한 경우 |
| `evidenceMismatch` | 7 | dbSNP·NM/MD처럼 진단에만 묶인 용어를 말하면서 그 진단 근거를 인용하지 않음, 한정 조건(필터 전 변이)을 어디에도 인용하지 않음 |
| `docEvidenceMisuse` | 8 | 주요 발견·한계 항목이 공식 문서(`doc:`, `manual:`)만 인용함 |

Gate 1(CLI의 JSON schema 강제)은 Claude CLI 안에서 일어나므로 오프라인으로 재현할 수 없다. 이번 실험 대상이 아니다.

## 데이터

후보: 저장된 평가 기록 29개 (`evals/baselines/*.json` 23개, `experiments/ab_2026-11-04/[AB]_r*.json` 6개).

원본 응답이 다음 조건을 **모두** 만족할 때만 "평가 가능한 원본"으로 쓴다.

1. 답변(`output`)이 있다.
2. 그 case의 payload를 모델 호출 없이 다시 만들 수 있다 (capture, archive, 합성 case, fixture).
3. Tool이 연 단계의 증거를 같은 Run 복원본에서 다시 읽을 수 있고, 근거 ID가 기록과 같다.
4. 현재 검사로 원본이 통과한다. 원본이 이미 걸리면 주입한 오류의 효과를 가를 수 없으므로 주입 실험에서는 빼고 "오차단 후보"로 따로 본다.

재구성한 payload의 해시를 기록의 `payloadHash`와 비교해 결과에 적는다. 해시가 다르면 Knowledge나 contract가 바뀐 뒤라는 뜻이다. 이때는 "현재 payload 기준" 실험으로 표시한다.

**정상 답변이라는 독립 근거.** 기록의 사람 검토 칸 상태를 그대로 옮겨 적는다. 사람이 사실 정확성을 판정한 기록이 없으면 "독립 근거 없음"으로 둔다. 이 경우 오차단은 "기록 당시 제공된 답변을 현재 검사가 거부함"으로만 정의하고, 거부 사유를 하나씩 읽어 판단한다.

## 주입 방법

- 원본은 읽기만 한다. `copy.deepcopy`한 복사본에 **한 가지 유형의 오류만** 넣는다.
- 주입 결과는 검사 함수와 별개로 확인한다. 문자열이나 ID가 실제로 바뀌었는지, 넣은 값이 사실과 정말 다른지를 본다. 확인에 실패하면 그 시행은 "주입 실패"로 빼고 센다.
- 해당 사실이 payload에 없는 case는 "적용 불가"로 따로 센다. 예: 커버리지가 없는 실패 Run에 평균 깊이 오류를 넣을 수는 없다.

### 설계 범위 안 (지원 유형 — 탐지율 분모)

| ID | 오류 | 기대 검사 |
|---|---|---|
| S1 | 없는 근거 ID 하나를 첫 인용 항목에 추가 | unknownEvidenceRef |
| S2 | 사실에 있는 21 이상 숫자 하나를 사실에 없는 값으로 바꿈 (없으면 없는 값 문장 추가) | unsupportedNumber |
| S3 | payload의 camelCase 키 하나를 문장에 넣음 | internalFieldName |
| S4a | 서버 경로 모양 문자열을 문장에 넣음 | sensitiveOutput |
| S4b | 이 Run의 식별자(sample/run id)를 문장에 넣음. job 행이 있는 case만 | sensitiveOutput |
| S5 | "평균 깊이는 N배" 문장. N은 사실 집합에 있지만 다른 항목의 값이라 Gate 4를 통과함 | runFactMismatch |
| S6 | "경고로 끝난 단계는 모두 k개" 문장. k ≠ 실제 수, k ≤ 20이라 Gate 4를 통과함 | runFactMismatch |
| S7 | 진단 전용 용어(dbSNP 등)를 말하는 항목을 추가하고 그 진단 근거는 인용하지 않음 | evidenceMismatch |
| S8 | 첫 주요 발견 항목의 인용을 허용된 공식 문서 ID 하나로만 바꿈 | docEvidenceMisuse |
| S9 | 첫 주요 발견 항목의 `evidenceRefs`를 빈 목록으로 만듦 | invalidSynthesis |

### 설계 범위 밖 (한계 평가 — 지원 유형 분모에 섞지 않음)

| ID | 오류 |
|---|---|
| U1 | 실행 상태를 뒤집는 문장. 실패 Run에 "정상적으로 끝남", 완료 Run에 "입력 검증에서 중단" |
| U2 | 근거 없는 원인 관계 주장 ("참조 유전체 버전이 맞지 않아서 생긴 것") |
| U3 | 실패 단계 바꿔 말하기 ("변이 검출 단계에서 발생") |
| U4 | 틀린 작은 정수 ("실패한 단계는 7개") |
| U5 | 틀린 정의 ("평균 깊이는 덮인 비율을 뜻함", 숫자 없음) |
| U6 | 사실에 있는 숫자를 다른 주어에 붙임 (Gate 6이 추적하지 않는 주어: "전체 실행 시간은 N초") |

## 지표

- 원본 수, 평가 가능한 원본 수, 제외 수와 사유
- 정상 통과 수와 오차단 수 (분모 = 평가 가능 후보 원본)
- 유형별 실험 수, 탐지 수(어느 검사든 거부), 기대 검사 탐지 수, 미탐지 수, 적용 불가 수, 주입 실패 수
- 검사별 차단 결과 (어떤 주입에서 어떤 검사가 걸렸나)
- 실제 거부 기록 재현: 답변이 없는 기록 중 `rejectedOutput`이 남은 기록을 현재 검사로 다시 돌린 결과

## 이번 실험의 잠정 성공 기준 (2026-11-21 설정)

과거에 정한 목표가 아니다. 이 실험을 해석하려고 실행 전에 정한 값이다.

- 지원 유형별 탐지율 ≥ 95%. 기대 검사 기준으로 따로도 본다.
- 평가 가능 원본 중 오차단 0건.
- 범위 밖 유형에는 기준을 두지 않는다. 탐지 수만 보고한다.

## 1차 실행 뒤 추가한 것 (2026-11-21, 사후 추가)

1차 실행에서 S5는 모든 시행이 같은 값(100) 하나만 넣었고, S6도 같은 수(실제 + 2)만 넣었다. 값이 하나뿐이면 탐지 결과가 그 값에만 해당할 수 있어서 아래 시행을 추가했다. 1차 결과를 본 뒤에 정한 것이므로 결과 보고에서 구분한다. 1차 행(S1~S9, U1~U6)의 정의는 바꾸지 않았다.

- S5v: 답변마다 사실 집합의 다른 값(21 이상 정수, 최대 5개)을 각각 "평균 깊이는 N배"로 넣음. 기대 검사 runFactMismatch
- S6v: 경고 단계 수를 실제 + 1, + 2, + 3으로 각각 넣음. 기대 검사 runFactMismatch
- U7 (범위 밖 문형): 평균 깊이 오류를 다른 문형으로 씀. "target 영역은 평균적으로 N번 정도 읽혔습니다", N은 사실에 있는 다른 값
- U8 (범위 밖 문형): 경고 단계 수 오류를 다른 문형으로 씀. "경고는 k개 단계에 걸쳐 나타났습니다"

## 안전

- Claude CLI를 부르지 않는다. `provider.run_structured`를 호출되면 예외가 나는 함수로 바꿔 둔다.
- 파이프라인, 서버, VM을 건드리지 않는다.
- Run 복원은 기존 eval의 임시 환경(`isolated_environment`)에서만 한다. capture와 archive는 읽기만 한다.
- 기존 기록과 DB에는 쓰지 않는다. 결과는 이 폴더의 새 파일에만 쓴다.
- 결과 파일에는 sample/run 식별자 문자열을 남기지 않는다. S4b의 주입 문장은 자리표시자로 저장한다.
